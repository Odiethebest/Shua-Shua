## 0. 五项重点核查 —— 先给裁决

这五件事决定你能不能用某些词，所以放在最前面。

### (a) DAG 调度器是真拓扑排序，还是写死的线性链？

**裁决：写死的顺序调用。不是拓扑排序。**

`src/pipeline.hpp:24-42` 全文（有效代码 19 行）：

```cpp
void add(std::unique_ptr<Operator> op) { nodes_.push_back(std::move(op)); }   // :26-28

Batch run(const Batch& seed, std::vector<TraceEntry>& trace) const {          // :32
    Batch batch = seed;                                                       // :33
    for (const std::unique_ptr<Operator>& node : nodes_) {                    // :34
        batch = node->run(batch, trace);                                      // :35
    }
    return batch;
}
std::vector<std::unique_ptr<Operator>> nodes_;                                // :41
```

**没有**：依赖声明、边、入度表、拓扑排序、环检测、多输入节点、并行、子图选择。
`nodes_` 是 `vector`，`run` 是 `for`。

代码注释是**诚实的**（`:11-22` 自称 "degenerate DAG: one path, no branches"），
问题在命名对外的暗示：类名 `Pipeline`、UI 写 "DAG pipeline trace"
（`TracePanel.tsx:51`）、README 写 "DAG of operators"。

> **结论：面试里说「我实现了 DAG 调度」是虚的。**
> 能说的是「我把算子抽象成统一接口，由一个调度器串起来并统一采集 trace；
> 它目前是线性链，我在注释里写明了这是 degenerate DAG」。
> 补齐方案与工作量见 §3 的 F2/F3。

### (b) 新增算子要改几个文件？

**裁决：这一条是真的强。实测（grep 全仓库）——**

```
$ grep -rn "RecallOp|FeatureOp|ScoreOp|RerankOp|MixOp" src/ web/src/ \
    | grep -v <各算子自己的头文件>
```

除注释外，**具体算子类名在代码里只出现在一个函数中**：
`api.hpp:113-136` 的 `run_recommendation`，外加 `api.hpp:11-19` 的 include。

| 场景 | 需要改动 |
|---|---|
| **加一个不引入新特征列的算子**（如 DedupOp / FilterOp） | **1 个新文件** `src/xxx_op.hpp`<br>**1 个文件改 2 处**：`api.hpp` 加 `#include` + 加一行 `pipeline.add(...)` |
| 加一个**引入新特征列**的算子 | 再加 3 处：`operator.hpp:22-29` 的 `Candidate` 加字段、`api.hpp:195-201` 的 `to_json` 加输出、`web/src/engine.ts:10-18` 的 `FeedItem` 加类型 |

**不需要改**：`Pipeline`（完全不认识具体算子）、`Operator` 基类、
**整个前端**。

前端这点是实测的：`TracePanel.tsx:63` 是 `trace.map((e, i) => ...)`，
`key={e.name}`，逐节点渲染名字/in/out/latency/detail **全部来自数据**。
`web/src/` 里所有出现算子名的地方**都是注释**（`engine.ts:26`、
`presentation.ts:162`、`profile.ts:42`、`TracePanel.tsx:29,35`），
没有一处是代码分支。

> **结论：「新增算子不改调度器、不改前端」是可以主动讲的。** 这是 §2 表里
> 少数几个【强对应】之一，也正是 bullet 2/5 的 "operator migration" 想解决的解耦。
> 唯一的附加成本是运维步骤：改完要重新 `bash scripts/build-wasm.sh` 并**重新提交产物**。

### (c) 图结构是硬编码还是从配置读？

**裁决：硬编码在 C++ 里，而且超参也是。**

- 图拓扑：`api.hpp:113-136`，`pipeline.add(...)` 手写五次，

> **结论：这是与 bullet 1「DAG-DSL」差距最大、也最值钱的一个缺口。**

### (d) 逐节点 trace 是否可按需开关、是否带耗时和输入输出规模？

**裁决：内容够，开关没有。**

`TraceEntry`（`operator.hpp:41-48`）每个节点采集：
`name` / `in_count` / `out_count` / `latency_us`（`steady_clock`，`:83-91`）/
`sample_ids`（前 5 个输出 id，`:105-113`）/ `detail`（一行自定义说明）。
**这已经覆盖了 bullet 4「each node's execution details」的实质内容。**

但它 **永远全开**，没有任何开关：`Operator::run`（`:79-96`）无条件计时、
无条件 `trace.push_back`。没有编译期 flag，没有运行时 level，没有 per-node 过滤。
和 bullet 4 的 "**gflags to control on-demand logging**" 差的就是这一层。

> **结论：内容可以讲，「按需」不能讲。** 补齐见 §3 **F4**（最便宜的一项，2–3h）。

### 能力点 7 展开：diff 一致性校验的六个组成

这是对标 bullet 6 的核心，逐条指到代码：

| 组成 | 位置 | 作用 |
|---|---|---|
| ① 逐元素数值对拍 | `bench_parity.cpp:78-96` | 全部 3,000 个 item 的点积逐个比对，取 `max|naive-simd|`，不是只看 top-k |
| ② 集合对拍 | `bench_parity.cpp:108-114` | top-300 排序后比 id 集合是否相等 |
| ③ 序对拍 | `bench_parity.cpp:100-107` | top-300 逐位置比 id，`positional_diff` |
| ④ id tiebreak 消除伪 diff | `recall_op.hpp:66-70` | 分数相同按 id 升序。若不这么做，SIMD 求和顺序不同 → 并列项顺序可能不同 → **产生与 kernel 无关的假差异** |
| ⑤ 固定种子保证可复现 | `api.hpp:46` `kSeed=42`；`synthetic.hpp:55-58` | 注释明写："unseeded source would make 'result diff = 0' impossible to trust" |
| ⑥ 共用扫描逻辑做控制变量 | `recall_op.hpp:83-97` | 两个 kernel 都走 `recall_with`，**排序逻辑共享**，所以差异只可能来自 kernel 本身 |

**④ 和 ⑥ 是这套东西里最值钱的两条**，因为它们体现的是"设计对照实验"的意识，
而不只是"写了个比较"。⑥ 尤其是控制变量法的教科书用法。

另外两个可以主动讲的细节：

- **3,000 个里只有 583 个逐位相同**（官方运行）——80% 有差异，但全在 1e-7 量级、
  不影响排序。**这说明判据必须是"量级 + 排序不变"，不能是"逐位相等"。**
- 差异有**两个**来源：求和顺序重排，以及 `fmla` 融合乘加（单次舍入）vs
  `fmul`+`fadd`（两次舍入）。而且**融合让 SIMD 路径更准**——对 double 参考，
  SIMD 更接近真值的占 57.7%，scalar 22.9%，平均误差小 2.19 倍
  （`src/main.cpp:66-86` 记录了这个结论）。

### F5. WASM SIMD 分支（补上"部署产物 = 验证产物"）

| | |

## 5. 【红线清单】—— 绝对不能说的话

> 原则：**bench/ 是个人项目的验证脚手架，不是线上流量的迁移校验体系。**
> 凡涉及生产环境、灰度、多人协作、迁移规模、真实 QPS，一律不说。

| # | 不能说 | 为什么不能说 | 被问到时怎么诚实转场 |
|---|---|---|---|
| 1 | 「我做过算子迁移」「我迁移了 N 个算子」 | **没有迁移对象**。这是从零写的 5 个算子，不是把存量算子搬到新框架 | 「我没做过迁移。我做的是从零设计算子接口，所以我理解的是**接口该长什么样才让迁移不痛**——比如我这里加一个算子不用改调度器和前端。真实迁移难在存量算子的隐式依赖和行为等价性，那部分我只有推测。」 |
| 2 | 「零故障上线」「平滑迁移」「分批 rollout」 | **没有线上流量**。静态页，无后端，无用户 | 「我没有线上环境。我能讲的是**变更前后一致性校验**这件事本身怎么做——对照实验怎么设计、判据怎么定、怎么保证校验自身有效。」 |
| 3 | 「灰度发布」「A/B 实验」「指标对齐」 | 无实验框架、无指标、无流量分桶 | 「A/B 我没做过。我做的是离线的确定性 diff：同一批输入、两种实现、逐元素比对。这只能证明**等价性**，证明不了**收益**——收益必须靠线上实验，这是两件事。」 |
| 4 | 「支撑 X QPS」「服务 N 用户」「P99 延迟 Y ms」 | **从未做过并发压测**。单线程、单请求，连 Web Worker 都没有（实测 grep 无) | 「我没测过吞吐，这是单线程单请求的引擎。我测的是单次请求的延迟构成和瓶颈分布。要谈 QPS 得先解决并发模型——我现在连 Worker 都没上，整条 pipeline 是阻塞浏览器主线程的。」 |

### 转场的通用句式

被问到任何"你没有的经验"时，用同一个三段式：

1. **直接承认**，不铺垫、不模糊（"我没做过 X。"）
2. **给出你确实有的、最接近的那一层**，并带证据（"我做的是 Y，具体是……"）
3. **说清两者的差距在哪**（"X 真正难的是 Z，那部分我只有推测。"）

第 3 步是关键：**能准确说出自己不懂的部分难在哪，本身就是一种能力证明**，
而且它把对话从"考核你有没有"转成"讨论这件事本身"。

## 6. 这一步最重要的四个结论

1. **最强的三张牌不在算法，在工程纪律上**：统一算子接口（加算子不改调度器和前端，
   grep 实测）、数值对拍的对照实验设计（共用排序逻辑 + id tiebreak）、
   以及**校验自身的可信度**（`--simulate-mismatch` + CI 断言门禁能红）。
   第三条大多数候选人没有。

2. **最值钱的缺口是 F1（配置化建图），8–12 小时。** 做完之后
   「配置驱动的 DAG」这句话才成立，直接对上 bullet 1。配 F3（trace 开关，2–3h）
   一起做，11–15 小时能同时点亮 bullet 1 和 bullet 4。

3. **`clickHistory` 是个已经躺在那里、但没被用的资产**（`profile.ts:45-49`
   在采集完整的 `{itemId, tags, timestamp}` 序列，全仓库却只取了 `.length`）。
   这是 bullet 7 唯一够得着的入口，边际成本低。

4. **"DAG" 这个词现在是虚的，"on-demand" 也是。** 这两个词恰好是那位 intern
   bullet 里出现频率最高的，所以**要么花时间补齐（F1+F2+F3），要么在面试里
   严格避开**。含糊其辞是最差的选项——面试官只要问一句"你的拓扑排序怎么实现的"
   就会穿帮。
