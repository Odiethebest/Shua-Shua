## 1. 90 秒项目自述

### 中文版

> 刷刷是一个用 C++20 写、编译成 WebAssembly 在浏览器里跑的**推荐 serving 引擎**。
> 它只做在线服务这一半——召回、特征、打分、重排、混排——不做训练，
> 因为我想把深度放在工程上而不是建模上。
>
> 结构上，五个阶段都实现同一个算子接口。基类的 `run()` 不是虚函数，
> 子类只实现 `transform()`，**计时和 trace 的组装在基类做一次**，
> 所以每个算子的观测数据结构上不可能不一致。这个解耦是可验证的：
> 我 grep 过全仓库，具体算子类名只出现在一个装配函数里——
> **加一个算子只要新增一个头文件、在装配处加两行，执行器、算子基类、
> 整个前端都不用动**，因为前端是逐节点渲染 trace 数组的，不认识任何具体算子。
>
> 性能上，召回的内积我手写了 NEON。但我想讲的不是加速比，是**验证**：
> 我对全部 3,000 个候选做逐元素数值对拍，最大偏差 2.98e-07，
> top-300 排序零差异。它现在是 CI 门禁，而且 CI 里有一步专门注入错误、
> 断言这个门禁必须变红——**一个从没红过的检查不算检查**。
>
> 最后，整条流水线的每一级都会自报输入输出规模和真实耗时，前端渲染成漏斗。
> 我也量化过这个观测工具自己的盲区：它只覆盖一次请求耗时的 88.3%，
> 算上序列化是 74.7%。

### English version

> Shua Shua is a **recommendation serving engine** written in C++20 and compiled
> to WebAssembly so it runs entirely in the browser. It implements only the
> serving half — recall, feature attachment, scoring, reranking, mixing — and no
> training, because I wanted the depth to be in the engineering rather than in
> modelling.
>
> Structurally, all five stages implement one operator interface. The base
> class's `run()` is non-virtual; subclasses implement only `transform()`, and
> **timing plus trace assembly happen once in the base**, so no stage can report
> inconsistently. That decoupling is verifiable rather than aspirational: the
> concrete operator class names appear in exactly one assembly function, so
> **adding an operator means one new header and two lines — the executor, the
> operator base class and the entire frontend stay untouched**, because the
> frontend renders whatever nodes the trace array contains and knows no operator
> by name.
>
> On performance I hand-wrote a NEON inner product. The part I care about isn't
> the speedup, it's the **verification**: an element-wise numerical diff against
> the scalar reference across all 3,000 candidates, max deviation 2.98e-07, zero
> difference in the top-300 ranking. It's a CI gate now — and CI has a step that
> injects a mismatch on purpose to assert the gate can go red, because **a check
> that has never failed isn't known to be a check**.
>
> Finally, every stage self-reports its input and output cardinality and real
> latency, which the frontend renders as a funnel. I've also quantified that
> tool's own blind spot: it accounts for 88.3% of a request, or 74.7% once
> serialisation is counted.

## 2. 三分钟深入版

> 先说清边界：这是推荐系统的 **serving** 一半。没有训练、没有学习到的
> embedding、没有线上流量。所以任何关于模型效果的问题我都答不了，
> 但流水线本身是真的。
>
> **数据布局。** item 的 embedding 放在一个扁平 float buffer 里，
> 元数据放在平行数组，扫描时不把元数据拖进 cache。这里我要区分两件常被混为一谈的事：
> **向量化需要的是单个 item 的 64 个 float 连续，不是这个布局本身**——
> 我做过对照实验，AoS 版本跑同一个 kernel 速度落在同一个噪声区间。
> 所以「SoA 是为了上 SIMD」这个说法是错的。
>
> **算子与执行。** 五个阶段：召回全量扫 3,000 个候选取 top-300，
> 特征层挂三列，打分层线性融合后截到 50，重排用 greedy MMR 以类目为冗余轴做多样性，
> 最后混排组装 12 条的页面并保留 2 个探索位。
> 这五个都实现同一个接口，由一个执行器串起来。
> **这个执行器我最近把它从 `DagScheduler` 改名成了 `Pipeline`**，
> 因为它就是顺序执行，旧名字承诺了代码没有的东西。
> 我在头注释里写清了真要成为 DAG 缺的是什么——不是拓扑排序，
> 拓扑排序在一条直线上是空操作；缺的是分叉和**扇入**，
> 因为一旦某个节点有两个输入，`run()` 就不能只串一个 batch，
> 算子契约本身要长出「多个输入怎么合并」的规则。
>
> **热点与验证。** 唯一的热计算是召回的内积：3,000 次点积 × 64 维 = 192,000 次乘加。
> 我手写了 NEON，沿维度四路展开。反汇编之后有个反直觉的发现：
> **标量参考的乘法其实已经被编译器向量化了**，只有加法是串行的，
> 所以加速比真正来自「归约被向量化」——依赖链从 64 缩到 16。
>
> 验证这块我做了三层。第一层是逐元素数值对拍，判据是量级容差加排序不变，
> **不是逐位相等**——因为 3,000 个里只有 583 个逐位相同，
> 八成的结果都有 1e-7 量级差异。第二层是让对拍本身可信：
> 两条路径**共用同一套排序逻辑**，所以差异只可能来自 kernel；
> 并且分数相同时按 id 兜底排序，否则求和顺序不同会造出与 kernel 无关的假差异。
> 第三层是让门禁可信：注入错误的负向测试，CI 里断言它必须失败。
>
> **然后是我觉得最有意思的部分。** 优化完之后我重新 profile，
> 发现瓶颈已经不在扫描了：SIMD 在扫描上是 3.09×，但**端到端召回只有 1.57×**，
> 因为 top-k 排序是两条路径共享且没被向量化的。它现在占召回耗时的 81.6%。
> 换成 `nth_element` 还能再快 2.69×——**比 SIMD 带来的还多**——
> 而且我验证过它产出完全相同的 top-300。这个我还没做，它在我的清单上。
>
> **最后是可观测性。** trace 是这个项目的产品，所以我也去量了它的覆盖率：
> 88.3%，算上 JSON 序列化 74.7%。差的那部分是种子池构造、执行器的拷贝和序列化，
> 它们结构性地落在所有算子的计时器之外。浏览器侧还有 23.3% 的墙钟花在
> 文本边界上，那部分 trace 完全看不见。

## 3. 二十个高频追问

### A 档 · 基础理解（1–7）

| # | 问题 | 答题要点 |
|---|---|---|
| 1 | 走一遍一次请求的完整链路 | 点刷新 → 画像先衰减一步（每个 tag ×0.5）→ 折成 6 个类目权重 → CSV 过 embind 边界 → C++ 把 6 个权重加权合成 **1 个 64 维单位向量** → 五个算子顺序执行 → 手写 JSON 回传 → `JSON.parse` → 渲染漏斗和瀑布流。**唯一的异步点是首次加载引擎**，之后 C++ 调用是同步的 |
| 2 | 为什么点积就是余弦相似度 | item 向量和 query 都做了单位归一化，所以点积 = cos。好处是 kernel 保持最简，"相似"= 方向一致，与类目聚类对齐 |
| 3 | `Candidate` 里的字段为什么是逐级填充的 | 每一级只负责自己那几列：召回填 similarity，特征层填三列，打分层填 score。**未产出前默认 0**。这让每级职责边界很清楚，也让 trace 能看出每级在做什么 |
| 4 | 特征层的 recency 为什么用指数衰减 | 指数天然落在 (0,1] 不用 clamp，且形状符合"先快后慢"。半衰期 30 天是**拍的**——这是个 demo 常数，真实系统该由数据定 |
| 5 | MMR 是什么，λ 起什么作用 | 每轮挑边际价值最高的：`λ·score − (1−λ)·同类已选数`。λ=1 纯相关性，λ=0 纯打散。这里用**类目重叠**而不是向量相似度做冗余信号，因为这个 feed 的"单调"轴就是类目 |
| 6 | 为什么要有探索保底 | 对一个集中的 query，召回回来的 300 个几乎全是同一类目，**排序阶段看到的每个候选都是那个类目**——多样性不可能从已排序的池子里涌现，必须注入。所以保留固定槽位 |
| 7 | trace 里都有什么，为什么是固定结构 | name / 输入规模 / 输出规模 / 真实耗时 / 输出样本 id / 一行自定义说明。固定是因为前端按数组逐节点渲染，**结构一变 UI 就得跟着改**，所以它是契约 |

### B 档 · 设计权衡（8–14）

| # | 问题 | 答题要点 |
|---|---|---|
| 8 | 为什么 trace 要放在基类而不是每个算子自己写 | 一致性。放基类是 template method：`run()` 非虚，`transform()` 是 protected 纯虚，**子类没有能力绕过或写得不一致**。放各算子里就是同样的样板复制五遍，任何一个漏填 sample_ids 都发现不了 |
| 9 | 为什么召回不读上游输入 | 它是 **source node**——没有数据前驱，从图外的资源产出。它顺序流式扫连续 buffer，改成"遍历入参 id 列表再取向量"会变成散乱 gather，把布局优势浪费掉。种子 batch 存在是为了给统一的 in_count 契约一个漏斗口径，代价约 9µs |
| 10 | SoA 到底买到了什么 | 拆两层讲。**扫描时不把元数据拖进 cache**——方向上少读 6.2% 的字节。但幅度：我 9 次独立试验测下来全距 −4.7%…+4.4%，**跨零，测不出来**，因为 768 KB 全进 L2。而 **SIMD 需要的是 embedding 块连续，AoS 也满足**——这是两个收益 |
| 11 | 为什么打分是线性加权而不是模型 | 因为没有模型。训练不在范围内，所以我用透明的线性式，而不是造一个假的 sigmoid 曲线来显得像模型。四个权重是手调的——**没有离线评估集就没法调参**，真实做法是离线 AUC 加线上实验 |
| 12 | 为什么衰减按刷新触发而不是按时间 | 点击驱动的场景里几乎不流逝真实时间，用 `exp(-λΔt)` 会看起来什么都不淡。事件驱动让淡出恰好发生在用户操作时。**因子从 0.7 调到 0.5 是有记录的**：0.7 时早期点击太久不掉，画像感觉被锁死。动力学上 `w ← (w+c)×0.5` 的不动点是 c，也就是每轮点击数，所以天然有界 |
| 13 | 跨语言边界为什么用字符串 | 6 个 float 这种固定小向量，CSV 是最简单稳健的过界方式。代价我量过：payload 一次请求物化 5 遍，占浏览器墙钟 23.3%。**在 2 KB 量级这是对的工程选择**；真到更大量级就得换二进制协议——但这是我知道，不是我做过 |
| 14 | 为什么用 min-of-rounds 而不是平均 | 噪声只会让时间变长，所以最小值是最可复现的统计量；平均值会随后台负载漂移。而且比较两个变体时我**逐轮交错**，让热身升温对两边影响一样。但比较总量和分量时我用平均——**因为那要求两个数来自同一批观测** |

### C 档 · 压力深挖（15–20）

#### 15. 「你候选池才 3,000，凭什么说自己懂大规模检索？」

**不辩解，直接让掉。**

> 「我不懂大规模检索的工程，这个我不装。我的池子是 3,000，全量暴力扫，
> 没有 ANN 索引、没有分片、没有 GPU。
>
> 这个规模下我能讲清楚的是别的东西：SIMD 的收益具体从哪来（依赖链缩短，
> 有反汇编）、优化完之后瓶颈会转移到哪（top-k 排序，占 81.6%，有实测）、
> 以及怎么证明一个优化没改变结果。
>
> 真到 10⁶ 以上我知道要换 ANN 加分片加量化，但那部分我只有书本认知。
> 我更愿意讲我实测过的东西。」

#### 16. 「SIMD 在真实 serving 里到底有没有意义？」

**这题要用你自己的数据来答，而不是辩护。**

> 「在我的项目里，意义比我一开始以为的小——而这个发现本身是有意义的。
>
> 扫描上是 3.09×，但**端到端召回只有 1.57×**，因为 top-k 排序是共享的、
> 没被向量化。优化完之后我重新 profile，排序占了召回的 81.6%，
> 换 `nth_element` 能再快 2.69×,**比 SIMD 带来的还多**。
>
> 所以我的结论是：SIMD 在这里是**正确的第一步**——优化前扫描确实是大头——
> 但如果只报 3.09× 而不说端到端 1.57×，那是在误导。真实 serving 里
> 内积通常也不是瓶颈，瓶颈更可能在访存、在索引结构、在 RPC。
> SIMD 值不值得做，取决于 profile 说什么，不取决于它听起来先进。」

#### 17. 「你这个和一个函数调用链有什么区别？」

**这题的正确答法是承认大部分，然后守住小部分。**

> 「执行上没有区别，就是顺序调用。我最近把这个类从 `DagScheduler`
> 改名成了 `Pipeline`，就是因为旧名字承诺了代码没有的东西。
>
> 它比函数调用链多出来的只有两样，但这两样是真的：
> 第一，**算子可插拔**——加一个算子不用改执行器、不用改前端；
> 第二，它是**唯一收集 trace 的地方**，所以每一级的观测数据不可能格式跑偏。
>
> 真正的图能力——分叉、扇入、拓扑序——我没做。而且我想说清一点：
> **缺的不是拓扑排序算法**，一条直线的拓扑序就是它自己，加了也是空操作。
> 缺的是扇入：一旦一个节点有两个输入，`run()` 就不能只串一个 batch，
> 算子契约本身得长出多输入怎么合并的规则。那才是真正要设计的部分。」

#### 18. 「你没做过迁移，怎么理解算子迁移的难点？」

> 「我确实没做过迁移，我这五个算子是从零写的，没有存量。
>
> 我能讲的是从**接口设计**这一侧看到的东西。我做过一件事：
> grep 全仓库确认具体算子类名只出现在一个装配函数里，
> 所以加算子不用改执行器和前端。这让我理解迁移想解决的**耦合**长什么样——
> 如果算子的名字散落在调度器、序列化、UI 里，每搬一个都要改一圈。
>
> 但我也清楚真实迁移难的不是这个。难的是**行为等价性**：
> 存量算子有隐式依赖、有历史行为、有没人记得为什么的特例，
> 你搬完之后怎么证明输出没变。这一点上我唯一沾边的经验是
> 给 kernel 优化做数值对拍——对照实验怎么设计、判据定成什么、
> 怎么保证校验自身有效。**那是同一种思路，但不是同一个量级的问题。**」

#### 19. 「你的 parity check 在你实际部署的 WASM 产物上是平凡成立的，那它到底验证了什么？」

> **这题是这份材料里最尖锐的一个，先自答一遍。**

**它验证了 kernel，没有验证部署产物。这两个在这个项目里恰好不是同一个东西。**

拆开说：

**(1) 它真正验证了什么。** 在 native arm64 上，`__ARM_NEON` 有定义，
`dot_simd` 就是那份手写 NEON。对拍在那里是实打实的：3,000 个候选逐元素比对，
最大偏差 2.98e-07，top-300 零差异。**那份 kernel 的正确性是被证明了的。**

**(2) 它没有验证什么。** emcc 既不定义 `__ARM_NEON` 也不定义 `__wasm_simd128__`，
而且 `build-wasm.sh` 没有传 `-msimd128`，所以在 WASM 上
`dot_simd` 编译成 `return dot_scalar(...)`。**对拍在那里是拿一个函数和它自己比。**
这个我不是推测出来的——我把提交的 `shuashua.js` 里内嵌的 wasm 抠出来反汇编过，
**v128 指令数是 0**。

**(3) 所以风险到底是什么。** 关键在于：**线上跑的那条路径恰好就是参考实现本身。**
所以风险不是"部署了一个未经验证的、可能算错的东西"——
部署的就是那个最保守的标量版本。真实的风险有两条，都要说：
- **性能表述的风险**：如果我说"我的引擎用 SIMD 加速"，对线上那份就是假话。
- **流程的风险**：我的正确性门禁不覆盖我真正发布的构建。今天没出事是因为
  回退路径恰好是参考实现；如果哪天有人写了一个 WASM SIMD 分支，
  **它会在完全没有对拍覆盖的情况下上线**。

**(4) 怎么补。** 在 `dot.hpp` 加一个 `#elif defined(__wasm_simd128__)` 分支，
build 脚本加 `-msimd128`，再让同一套对拍在 Node 里针对真实的 `.wasm` 跑一遍。
大概 2–4 小时。我还实测过一个坑：**光加 `-msimd128` 没用**——
隔离编译单元里 baseline 和 `-msimd128` 发出的指令完全一样，
因为 clang 不会在没有 `-ffast-math` 的情况下向量化浮点归约，
而 `-ffast-math` 会毁掉对拍的前提。所以必须手写 intrinsics。

**(5) 一般性的教训**，这句是重点：
> **正确性门禁必须跑在你真正发布的那个产物上，而不是同一份源码的一个方便的构建上。**
> 我是通过去反汇编确认、而不是假设，才发现这件事的。

#### 20. 「你所有数字都是自己测的，我凭什么信？」

> 「你可以不信，所以我把它做成可复现的。
>
> 一条命令 `bash bench/run_all.sh`，所有数字都从这一条命令出来。
> 我钉了一次官方运行进 `bench/RESULTS.md`，记录机器型号、编译器版本、commit，
> **README 和所有文档只引这一份**，不允许出现别处测的数。
>
> 方法上：min-of-interleaved-rounds，变体逐轮交错；
> 每个 bench 打印自己的 harness 说明；
> 而且我明确列了**不能引用的数字**——比如无分配扫描的 4.46×，
> 它技术上是真的，但用它而不用 3.09× 属于选择性引用。
>
> 还有一个例子能说明我怎么对待自己的数：我一度写下'SoA 比 AoS 快约 4%'，
> 那是只跑了两次的结论。加大重复到 9 次以后全距跨零，
> 所以正确结论是**测不出来**。现在那个 benchmark 会自己检测跨零并**拒绝输出百分比**。」

## 4. 自我修正三例 ⭐ 全篇最重要的一节

> 这三段的作用不是展示技术，是展示**你怎么对待自己的结论**。
> 面试里能自然说出这三种话的人很少。**建议逐字背下来。**

### 例一 · 怀疑自己的检查

> 「我给 SIMD kernel 写了数值对拍之后，意识到一个问题：
> **这个检查从来没有失败过，所以我并不知道它真的能失败。**
> 一个永远绿的门禁和一个没有门禁，从证据上讲是一样的。
>
> 所以我加了一个 `--simulate-mismatch` 参数，
> 它会故意把一个候选的分数改掉 1.0，制造一次真实的不一致。
> 然后 CI 里有一步专门跑它，并断言**它必须返回非零**——
> 如果哪天这个注入的错误没能让门禁变红，说明门禁已经坏了，
> 那一步就会把整个 CI 标红。
>
> 我在 CI 日志里确认过它真的在工作：那一步打印的是
> 'gate correctly returned non-zero on an injected mismatch'。」

### 例二 · 推翻自己的结论

> 「我写过一个结论：SoA 布局比 AoS 快大约 4%。
> 那是基于两次测量——两次都是 +3.8% 和 +4.4%，看起来很一致。
>
> 后来我要把一次完整的基准运行钉成官方数据，那一次跑出来是 **−1.5%**，
> AoS 反而更快。这说明我原来的结论是**样本不足下的噪声读数**。
>
> 我没有去挑一次好看的结果，而是把那个 benchmark 改成跑 9 次独立试验并报告全距。
> 结果是 −4.7% 到 +4.4%，**跨过零**，9 次里 SoA 只赢 6 次。
> 所以正确的结论是：在 3,000 个 item、768 KB 全进 L2 的规模下，
> 这个差异**测不出来**。
>
> 现在那个 benchmark 会自己检测全距是否跨零，跨零时**拒绝输出百分比**，
> 只输出'不可分辨'。我觉得这比留一个好看的数字有用——
> **几个百分点的效应，没有重复试验就不该报数。**」

### 例三 · 承认自己的盲区

> 「我的 README 里曾经有一个 SIMD 徽章写着 NEON / AVX2，
> 还有一句'加速 3.6 倍'。我后来去核对，两个都站不住。
>
> AVX2 是仓库里**一行都没有**的东西。而 3.6 倍是扫描单独的数字，
> 端到端召回只有 1.57 倍。
>
> 更严重的是第三件事。我去查了一下浏览器里到底跑的是哪条路径:
> emcc 不定义 `__ARM_NEON`，所以 `dot_simd` 编译成标量回退。
> 我不满足于推理，就把提交的那个单文件 WASM 里内嵌的二进制抠出来，
> 用 Binaryen 反汇编，**grep v128 指令，数量是 0**。
>
> 也就是说：**我部署的产物里根本没有 SIMD，而我的正确性检查
> 在那个产物上是平凡成立的。** 我把这条列在待补清单的第一位，
> 并且在 README 里明确写了 native-only。
>
> 我讲这个是因为——**知道自己的验证覆盖不到哪里，
> 比多一个通过的测试更重要。**」

## 5. 已知 backlog

> 这一节的作用是把"没做"变成"知道该做什么、值多少、以及为什么现在没做"。
> 被问到缺陷时，主动拿出这张表比逐条被挖出来好得多。

**口头版开场**：
> 「这个项目我有一张明确的待办清单，是我做完一轮自我审计之后列的，
> 按投入产出比排过序。我挑几个讲。」

| 项 | 缺什么 | 工时 | 补完之后能多说的那句话 |
|---|---|---|---|
| **1. trace 分级开关** | 逐节点的耗时和输入输出规模都采集了，但**永远全开**，没有任何开关 | 2–3 h | 「逐节点的执行细节是分级可控的，默认只记计数，排查时才打开耗时和样本 id——生产里全量 trace 的开销不可接受。」 |
| **2. 图与超参外置成声明式配置** | 流水线拓扑和全部超参**硬编码在一个函数里**，改一个数要重新编译 | 8–12 h | 「流水线拓扑和超参由一份声明式配置在启动时解析建图，算子通过注册表按名字实例化，**改排序策略不用重新编译**。」 |
| **3. 配置 A/B 的输出 diff** | 现在的对拍是 kernel 级的；没有"两种实现路径端到端结果一致"这一层 | 2–3 h（依赖 2） | 「把流水线从硬编码改成配置驱动时，我用一个 diff 工具验证改造前后在同一批 query 上输出完全一致，作为 CI 门禁。」 |
| **4. 真正的图能力** | 需要的不是拓扑排序，是**分叉 + 扇入**。最自然的入口是加第二路召回和一个归并去重节点 | 4–6 h（配置化后）+ 6–10 h（多路召回） | 「流水线是真的有向无环图：两路召回产出，归并节点去重后进入统一打分链路，按拓扑序执行。」 |
| **5. WASM SIMD 分支** | 部署的产物里 SIMD 指令数为 0，对拍在该 target 上平凡成立 | 2–4 h | 「三条内积实现共用同一套对拍，**在实际部署的那个 target 上也跑**，所以我发布的产物就是我验证过的产物。」 |
| **6. 行为序列特征** | 点击序列**已经在采集**（item id + 标签 + 时间戳），但只用了它的长度，从不跨边界 | 4–6 h | 「画像除了聚合的类目权重，还把最近 N 次点击的行为序列传进引擎，特征层用候选与序列的相似度做短期兴趣信号。」 |
| **7. `nth_element` 换掉全排序** | 已量化：占召回 81.6%，换掉能再快 2.69×，且验证产出相同 top-300 | < 1 h | 「召回里的 top-k 用 `nth_element`,比全排序快 2.69×,产出经验证完全一致。」 |
| **8. 引擎搬进 Web Worker** | 整条流水线**同步阻塞浏览器主线程**，全仓库没有 Worker | 3–4 h | 「引擎跑在 Worker 里，主线程不被阻塞。」 |

**为什么现在没做**（这句要能自然说出来）：
> 「优先级是按'能不能诚实多说一句话'排的，不是按难度。
> 第 7 项其实一小时就能做完，但它只是让一个数字更好看；
> 第 2 项要一天多，但它是唯一能让'配置驱动'这句话成立的。
> 我更愿意先补能力上的空白，而不是先摘低垂的果子。」

## 6. 项目真实短板清单

> 被问到"这个项目有什么问题"时用。**主动说比被挖出来好。**

## 7. 英文简历 bullet（3 条）

> 入选标准：数字必须在 `bench/RESULTS.md` 里指得到具体一行且能一条命令复现；
> 能力点必须是 `06-alignment.md` 的【强对应】。

**1.**
> Architected a C++20/WebAssembly cascade-ranking serving engine (recall → feature
> → score → rerank → mix) on a uniform operator interface that centralizes
> per-node tracing in the base class, so adding an operator touches one file and
> leaves the executor and the entire frontend unchanged.

**2.**
> Hand-wrote a NEON inner-product kernel and gated it with an element-wise
> numerical diff against the scalar reference over all 3,000 candidates (max
> deviation 2.98e-07, zero top-300 ranking difference), running in CI with an
> injected-mismatch test that proves the gate can fail.

**3.**
> Profiled the cascade to relocate its bottleneck: SIMD delivered 3.09× on the
> scan but 1.57× end-to-end, exposing the top-k sort as 81.6% of recall and a
> verified-equivalent `nth_element` swap worth a further 2.69×.

## 8. 临场提醒（一页纸）

**主动讲这三个**：统一算子接口的可验证解耦 · 对拍的对照实验设计 · 自我修正三例

**永远补的那半句**：
- 说 3.09× → 「这是扫描；端到端 1.57×」
- 说 SIMD → 「native only，浏览器里跑的是标量」
- 说 trace → 「覆盖 88.3%，含序列化 74.7%」
- 说 SoA → 「幅度测不出来；SIMD 需要的是块连续，不是 SoA」
- 说流水线 → 说「Pipeline」，不说「DAG 调度」

**被问到没有的东西**：直接承认 → 给最接近的那层 + 证据 → 说清差距难在哪。
第三步是关键。
