## A. 架构层

### A1. 只做 serving，不做 training 🟢

| | |
|---|---|
| **决策** | 只实现推荐系统的**在线服务**一半：recall → feature → score → rerank → mix。不做模型训练、不做离线评估、不做特征工程管线。 |
| **理由** | 目标岗位是 **Recommendation Infrastructure**，考察的是工程系统能力，不是建模能力。把 3 个月的精力摊到"训练 + serving"两头，结果会是两头都浅。`CLAUDE.md` 的 Scope discipline 明确写了这个取舍。 |
| **代价** | 所有"分数"都不是学出来的：ScoreOp 是线性加权（`score_op.hpp:41-44`），embedding 是合成的（`synthetic.hpp:94-116`）。**任何关于模型效果的问题都答不了**，也没有 AUC/GAUC/线上指标可谈。 |
| **重做会不会改** | 🟢 **不改**。这个边界划得对，而且划得清楚——`score_op.hpp:18-25` 明确拒绝造假的 sigmoid "模型"，宁可用一个诚实的线性式。**这个态度本身是加分项。** |

### A2. 无数据库、无后端、纯静态页 🟢

| | |
|---|---|
| **决策** | item store 是进程内内存单例（`api.hpp:60-63`），用户画像存浏览器 storage（`profile.ts:153-177`）。整个应用是一个静态页，部署在 Cloudflare Pages。 |
| **理由** | 一个"点开链接就能跑"的 demo，比一个"需要我帮你起服务"的 demo，在求职场景里价值高一个量级。而且无后端 = 无运维成本 = 项目不会因为服务器欠费而死。 |
| **代价** | ①候选池被内存和下载体积限死在 3,000（WASM 产物已 219 KB）；②没有真正的存储层，所以**没有任何 IO / 序列化 / 缓存 / 一致性问题可谈**——而这些恰恰是 infra 岗的核心；③画像不跨设备。 |
| **重做会不会改** | 🟢 **不改**，但要**主动补一句**："我知道这样规避掉了 infra 里最难的一半（存储与一致性）。" 与其被戳穿，不如自己说。 |

### A3. 编译到 WebAssembly ⚪

| | |
|---|---|
| **决策** | 用 Emscripten 把 C++ 引擎编成单文件 WASM（`scripts/build-wasm.sh:24-27`），在浏览器里直接跑。 |
| **理由** | 这是 A2 的必然结果：要让 C++ 引擎在无后端的静态页里跑，只有 WASM 这一条路。附带收益是"C++ 引擎跑在浏览器里"这件事本身有展示价值。 |
| **代价** | **代价比想象中大，而且是这次盘点才量化清楚的**：<br>① **SIMD 全丢**。emcc 不定义 `__ARM_NEON`（实测），`dot_simd` 编译进 `#else` 分支 = `dot_scalar`（`dot.hpp:86-90`）。反汇编提交的 `shuashua.js` 内嵌 wasm：**v128 指令数 = 0**。<br>② 加 `-msimd128` **也救不回来**——实测隔离 TU：baseline 与 `-msimd128` 都是 `8 f32.load / 4 f32.mul / 4 f32.add`，只有再加 `-ffast-math` 才出 `f32x4`。而 `-ffast-math` 会毁掉 parity check 的前提。<br>③ 边界只能走**文本序列化**：一次请求 payload 物化 5 遍（JS string → WASM 堆 → `stof` 解析 → `ostringstream` → 回 JS string → `JSON.parse`），实测 ~30 µs / 请求，占墙钟 27%。<br>④ 计时器要靠 COOP/COEP 才不被粗化（见 A4）。 |
| **重做会不会改** | ⚪ **取决于目的**。如果目的是"可点开的作品集"，WASM 是唯一解，不改。如果目的是"展示 serving 性能工程"，那 native + 一个小 HTTP 服务更诚实——SIMD 是真的、可以多线程、可以用 perf profile。<br>**当前的正确做法是保留 WASM，但在 README 和口头表述里严格区分 native / wasm target**（已在 commit `46b9ec3` 做了）。 |

### A4. 用 COOP/COEP 换高精度计时器 🟢

| | |
|---|---|
| **决策** | dev/preview（`vite.config.ts:12-15`）和生产（`web/public/_headers`）都发 `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp`。 |
| **理由** | 不跨域隔离时浏览器把 `performance.now()` 粗化，**µs 级的算子耗时全部读成 0**——而 trace 是这个项目的产品本身。`TracePanel.tsx:25` 读 `window.crossOriginIsolated`，为假时显示"timer clamped"提示（`:93-98`）。 |
| **代价** | 站点不能加载任何未带 CORP/CORS 头的跨域资源。这也是为什么封面图必须**本地化并提交**（650 张，`covers.ts:1-3`）而不能直接引 Unsplash CDN。 |
| **重做会不会改** | 🟢 **不改**。这是个漂亮的因果链：*trace 是产品 → trace 需要真数字 → 真数字需要跨域隔离 → 跨域隔离要求资源同源 → 所以图片必须本地化*。**面试里能完整讲出这条链，比讲十个算子有用。** |

### A5. 把 WASM 产物提交进 git ⚪

| | |
|---|---|
| **决策** | `web/public/shuashua.js`（219 KB）被有意提交，`.gitignore:19-24` 写明了理由。 |
| **理由** | Cloudflare Pages 的 CI 镜像没有 Emscripten，从仓库构建就必须有现成产物。 |
| **代价** | ①二进制产物进版本库，每次引擎改动都产生一个大 diff；②**存在源码与产物不同步的风险**——必须靠人记得重新 build 并 commit。 |
| **重做会不会改** | ⚪ 在"CF Pages + 无 Emscripten"这个约束下，**不改**。<br>**但风险可以消掉**：加一个 CI 步骤，重新 build WASM 并与仓库里的产物比对 hash，不一致就 fail。<br>本次盘点已实测：从当前源码重建的 wasm 与提交的产物 **SHA-256 完全一致**（`fde6772a…`），所以**现在是同步的**。 |

## B. 数据布局层

### B1. SoA 而非 AoS 🟢 —— **两个收益必须分开讲**

| | |
|---|---|
| **决策** | item embedding 放在**一个**扁平 `vector<float>` 里（`item_store.hpp:23`），per-item 元数据放在**平行**的 `vector<Note>`（`:24`）。`Note`（`note.hpp:15-26`）里**不含** embedding。 |

**⚠️ 这里有两个完全独立的收益，混为一谈会在面试里被戳穿：**

#### 收益一（SoA 真正买到的）：扫描时不加载无关字段

召回扫描只碰 embedding 数组，**完全不触碰 `notes`**。元数据（id / category /
popularity / age_days，16 B/item）从头到尾不进 cache。

如果换成 AoS —— `struct { float vec[64]; uint32 id; uint8 cat; float pop; uint32 age; }`
—— `sizeof` = **272 B**（256 B 向量 + 16 B 元数据，含对齐），扫描要拉
**816,000 B** 而不是 768,000 B，**多 6.2% 的访存**。

**实测这个收益有多大**（同一个 `dot_simd`，同一份数据，只有布局不同；
9 次独立试验，每次 20 轮 × 200 迭代交错取最小值 —— `bench/bench_layout.cpp`）：

## → 结论：**在这个规模下测不出差异。**

| | |
|---|---|
| SoA 优势，9 次试验全距 | **−4.7% … +4.4%** ← **跨零** |
| SoA 更快的试验数 | 6 / 9（≈ 抛硬币） |
| 官方运行那一次 | **−1.5%**（AoS 反而更快） |

全距跨过零、胜负接近五五开 → **这个效应落在 run-to-run 噪声里，无法分辨。**
`bench_layout.cpp` 现在会自己检测这一点，跨零时**拒绝输出百分比**。

> ⚠️ **不要引用任何百分比，包括中位数。** 一个跨零的分布，中位数没有意义。
> 唯一可以说的是"测不出来"。

**这条曾经被我写错，修正过程本身是面试材料。** 最初只跑两次、看到 +3.8% / +4.4%
就写下了"约 4%"；钉官方运行时那一次却是 −1.5%。改成 9 次独立试验后全距跨零，
说明原结论是**样本不足下的噪声读数**。能主动讲出"我以为有 4%，加大重复后发现跨零，
所以正确结论是测不出来"，比报一个好看的数字可信得多。

**正确的表述**：这个收益的**方向**是清楚的（少读 6.2% 的字节：`sizeof(ItemAoS)=272`
vs 纯向量每 item 256 B），但**幅度在 3,000 item / 768 KB 全进 L2 的规模下不可测**。
它要到 store 大到必须从 DRAM 流式读取时才会显著。

#### 收益二（SIMD 需要的，但**不是** SoA 给的）：embedding 块内连续

`dot_simd` 沿 **dim** 展开（`dot.hpp:57` 的循环变量是 `d`），
所以它需要的是**单个 item 的 64 个 float 在内存里连续**，
好让 `vld1q_f32(b + d)`（`:62`）一次装 4 个。

**AoS 布局里 `float vec[64]` 同样是连续的。** 上面的实验就是明证：
AoS 版本跑的是**一模一样的** `dot_simd`，速度落在同一个噪声区间里。

> **所以：向量化吃的是「embedding 块连续」，不是「SoA」。
> 说"我用 SoA 是为了能上 SIMD"是错的 —— AoS 一样能上。**

| | |
|---|---|
| **代价** | ①`count()` 由 buffer 长度推导（`:33-35`），且靠"id == 插入下标"省掉映射表（`synthetic.hpp:104-106`）→ **不支持删除/乱序 id**；②两个数组必须手工保持同步，没有类型系统保证。 |
| **重做会不会改** | 🟢 **不改**。但要能说清：这个布局是 **item-major**（`:18` 明写 "row-major by item"），**不是 dim-major**。真想跨 item 向量化（4 个 item 同时算、消除 3,000 次 horizontal reduction）才需要 dim-major，那是另一次重构。 |

**面试安全说法（背下来）**：
> 「embedding 和元数据分成平行数组，扫描时不把元数据拖进 cache——方向上少读 6.2% 的字节。
> 但我实测过：3,000 item 全进 L2，这个差异跨过零、测不出来，所以我不报百分比。
> SIMD 是另一回事：它沿 dim 展开，只要求单个 item 的 64 个 float 连续，AoS 同样满足——
> 对照实验里 AoS 跑的是一模一样的 kernel。所以这两个收益必须分开讲。」

### B2. DIM = 64、单位向量、合成数据 🟢

| | |
|---|---|
| **决策** | 固定 64 维（`item_store.hpp:21`）；所有 item 向量和 query 都归一化（`synthetic.hpp:40-51`、`api.hpp:76`）；数据由固定 seed 42 的 mt19937 生成（`api.hpp:46`、`synthetic.hpp:59-64`）。 |
| **理由** | ①归一化后**点积就是 cosine**，kernel 保持最简，且"相似"= 方向一致，与类目聚类对齐（`synthetic.hpp:33-39`）；②固定 seed 是 parity check 可信的前提——`synthetic.hpp:55-58` 明说"unseeded source would make 'result diff = 0' impossible to trust"；③64 维下随机 centroid 近似正交，噪声 σ=0.1 远小于 centroid 间距，所以同类聚得住（`synthetic.hpp:66-69`）。 |
| **代价** | embedding **不是学出来的**，只是"centroid + 噪声"。所以召回"有效"是被构造出来的，不能说明任何表征学习能力。 |
| **重做会不会改** | 🟢 **不改**。`synthetic.hpp:12-25` 自己就写了 "The content is fabricated; the ranking mechanism is real"——**这句话可以直接拿去面试用**。 |

## C. 调度与算子层

### C1. 「DAG」而非硬编码流水线 🟡 —— **本项目最需要小心的一条**

| | |
|---|---|
| **决策** | 有一个 `DagScheduler` 类（`scheduler.hpp:24-42`），算子通过 `add()` 注册，`run()` 顺序执行。 |
| **理由** | 相比在 `api.hpp` 里直接写 5 次函数调用，它买到两样真东西：①**算子可插拔**——加算子不用改 scheduler；②**统一的 trace 挂载点**——所有算子经同一条路径产出 trace。`scheduler.hpp:11-22` 明确解释了为什么**不做**通用 DAG 引擎：没有分支管线要调度，做了是投机性复杂度。 |
| **代价** | **实现是 19 行有效代码的 `for` 循环**：没有依赖声明、没有边、没有入度表、没有拓扑排序、没有环检测、没有多输入节点、没有并行。<br>**真正的代价不在代码，在命名**：类叫 `DagScheduler`、UI 叫 "DAG pipeline trace"（`TracePanel.tsx:51`）、README 叫 "DAG of operators"——**对外暗示的能力大于实现**。 |
| **重做会不会改** | 🟡 **取决于目标岗位，而这个岗位恰好需要它**。<br>作为纯工程判断：当前没有任何算子需要多输入，`scheduler.hpp:11-22` 的理由完全站得住，🟢 不改。<br>但作为**面向 BFS/DAG-DSL 岗位的作品集**：这是投入产出比最高的缺口。Step 6(a)/(c) 会给工作量评估。 |

**面试安全说法**：
> 「实现上它就是顺序执行，我在注释里写明了是 degenerate DAG。它比函数调用链多出来的是
> 算子可插拔 + 统一的 trace 挂载点。真正的 DAG 能力——多输入、拓扑序、并行——我没做，
> 因为这个管线里没有分支需要它。」
> **然后主动转到你真做了的解耦上（C2）。**

### C2. 统一算子接口 + 集中式 tracing（template method）🟢

| | |
|---|---|
| **决策** | `Operator::run()` 是 **non-virtual** 的，`transform()` 是 **protected pure virtual**（`operator.hpp:79-100`）。计时、组装 `TraceEntry`、push 全在基类做一次。 |
| **理由** | `operator.hpp:59-64` 写得很清楚：被否决的方案是"每个算子自己计时自己 push"——样板复制 5 遍，且任何一个算子都可能忘填 `sample_ids` 或格式跑偏。集中在一处**从结构上保证**了一致性。 |
| **代价** | ①算子**没有失败通道**——`transform` 返回 `Batch`，不返回 status 也不抛异常；②trace **不能关**，永远全开；③算子无生命周期（没有 `Init(config)` / `Close()`）；④`transform` 是 `const`，所以 MixOp 想报告"实际探索了几个"做不到，只能用 `detail()` 从**配置**推算（`mix_op.hpp:52-57` 承认了这点）——**detail 说的是配置意图，不是实际结果**。 |
| **重做会不会改** | 🟢 **不改，这是项目最强的一张牌**。template method 用在这里是教科书级别的正确：横切关注点只有一个（tracing），且必须绝对一致。<br>要补的是失败通道和 trace 开关（Step 6(b)(d)）。 |

### C3. RecallOp 作为 source node，忽略输入 batch 🟢

| | |
|---|---|
| **决策** | `transform(const Batch& /*in*/)`（`recall_op.hpp:117`）——参数名注释掉，不读输入。scheduler 用一个 3,000 元素的全量 seed batch 起头（`api.hpp:140`）。 |
| **理由** | 召回是候选的**产生者**（source node：无数据前驱，从图外资源产出）。它顺序流式扫 SoA buffer，这正是连续布局的收益所在；改成"遍历入参 id 列表再取向量"就成了散乱 gather，把布局优势全浪费（`:112-116`）。<br>seed batch 的作用是**给统一 trace 契约一个漏斗口径**——`Operator::run` 一律用 `in.items.size()` 填 `in_count`（`operator.hpp:89`），UI 漏斗宽度取 `max(e.in)`（`TracePanel.tsx:30`）。 |
| **代价** | 72,000 B 的 seed 被构造一次（`full_pool`，实测 7.49 µs）再拷贝一次（`scheduler.hpp:33`，1.46 µs）后被第一个算子完全忽略。**≈ 9 µs / 请求，约占整次调用 11%。** |
| **重做会不会改** | 🟢 **不改**，但要能说清替代方案：让 source node 自报 `in_count = store.count()`、seed 传空。更省，但要在基类开一个特例口子——**用 11% 换接口的无例外，是划算的。** |

### C4. top-k 用全量 `std::sort` 🔴 —— **实测已站不住**

| | |
|---|---|
| **决策** | `rank_topk`（`recall_op.hpp:63-73`）对全部 3,000 个候选做 `std::sort`，再 `resize(300)`。 |
| **原理由** | `:59-62`：「在这个 store 规模下差别可忽略，全排序 + 显式比较器是最一目了然的写法；`partial_sort` 在 n 变大后是合理优化——现在还为时过早（premature now）。」 |
| **代价（实测）** | 40 轮 × 100 次交错测量取最小值，两次独立运行误差 <3%：<br><br>`SIMD 扫描` **9.0 µs** ｜ `SIMD 扫描 + std::sort`（今天）**46.0 µs** ｜ `SIMD 扫描 + nth_element + sort(k)` **17.7 µs**<br><br>→ **排序占 recall 的 80%（37 µs / 46 µs）**<br>→ **M2 真正的端到端 recall speedup 只有 1.39×**（64.1 → 46.0），不是 3.6×<br>→ 换 `nth_element` 还能再快 **2.6×——比 SIMD 带来的收益还大** |
| **重做会不会改** | 🔴 **会改**。`:59-62` 那句 "premature now" **在当前规模下已经不成立**，实测推翻了它。<br>**但这不是"SIMD 白做了"**：M2 之前扫描占 64.1 µs 中的 26.7 µs（42%），优化它是合理的第一步；优化完瓶颈转移到排序——**这是 profiling 的正常节奏**。<br>**把这个完整故事讲出来，是回答「SIMD 在真实 serving 里有没有意义」的最佳弹药。** |

### C5. 线性加权打分，而非假模型 🟢

| | |
|---|---|
| **决策** | `score = 1.0·sim + 0.5·category + 0.3·recency + 0.2·popularity`（`score_op.hpp:41-44`，权重在 `api.hpp:118-119`）。 |
| **理由** | `score_op.hpp:18-25`：真实精排用学习模型预测多目标再融合；这里没有模型（训练不在范围），所以用透明的线性式。**"fabricated sigmoid 'model' curves would add mystery without adding a real model."** |
| **代价** | ①四个权重**是拍的**，没有离线评估集所以无法调参；②**特征没有量纲统一**——`category_match` 读的是未归一化的累计点击权重（`feature_op.hpp:43`，点击 +1 无上限），而其余三项都在 [0,1]。靠衰减隐式压在小范围（稳态 w\*≈每轮点击数），但这是运气不是设计。 |
| **重做会不会改** | 🟢 拒绝造假模型 **不改**，这个态度是加分项。<br>🔴 但**特征归一化会补上**——这是个明确的疏漏，不是取舍。 |

### C6. MMR 用类目重叠而非向量相似度 🟢

| | |
|---|---|
| **决策** | `value = λ·score − (1−λ)·(同类已选个数)`（`rerank_op.hpp:62`），λ=0.7。 |
| **理由** | `:26-31`：这个 feed 的"单调"轴就是类目——目标是别连着出 12 条美食。按类目直接命中这个诉求，且不用重新进点积 kernel。向量相似度 MMR 更通用，但在这里买不到什么，成本却是实打实的。 |
| **代价** | 只有一个多样性维度。同类目内部的重复（同作者、同话题）完全不管。λ=0.7 是拍的，没有多样性指标（ILD / entropy）来评估。 |
| **重做会不会改** | 🟢 **不改**。这是个对场景做对了的简化，理由写得清楚。 |

## D. 策略参数层（**这一层最容易被追问，也最容易露怯**）

### D1. exploration 比例 = 2/12 🟡

| | |
|---|---|
| **决策** | 每页 12 个槽位里，**保底 2 个**来自主导类目之外，随机采样、不参与排序（`api.hpp:52` `kExploreFloor=2`；`mix_op.hpp:91-121`）。 |
| **理由（这部分很扎实，要讲）** | `mix_op.hpp:29-33`：对一个集中的 query，recall 返回约 300 个**同类目** item，**排序阶段看到的每一个候选都是那个类目**。多样性**不可能从已排序的池子里涌现**，必须注入。所以保留固定槽位是唯一可靠的办法。<br>历史佐证：commit `1be623a` 的 message 就叫 "MixOp exploration floor — guaranteed diversity (filter-bubble fix)"。 |
| **代价** | ①**16.7% 这个数字是拍的**，没有实验依据；②探索项 `score/similarity/recency/popularity` 全是 0（`mix_op.hpp:116` 有意为之），导致前端 `whyFor`（`presentation.ts:165-181`）把它误标成 **"Trending right now"**——一个**表里不一的小瑕疵**；③它们被 append 在末尾，永远排在页面最后；④RNG 用 `seen_.size()` 做种子（`mix_op.hpp:109`），意味着**点击数相同的用户看到相同的探索项**。 |
| **重做会不会改** | 🟡 **机制不改，比例要靠实验定**。<br>诚实说法：「保底机制的**必要性**我能论证（过滤气泡是 recall 集中的必然结果，不是 bug）；但 **2/12 这个具体数字我定不了**——定它需要线上实验测'探索的长期留存收益 vs 短期 CTR 损失'，我没有这个闭环。」<br>**能讲清"为什么需要保底"比编一个比例数字强得多。** |

### D2. 衰减因子 = 0.5，且按刷新触发而非按时间 🟢 —— **唯一有调参记录的参数**

| | |
|---|---|
| **决策** | 每次点「Refresh」时，所有 tag 权重 ×0.5（`profile.ts:225,229`）。点击时 +1，无上限（`:200`）。 |
| **理由一（事件驱动 vs 时间驱动）** | `profile.ts:209-215`：在点击驱动的 demo 里几乎不流逝真实时间，用 `exp(-λΔt)` 会看起来"什么都不会淡"；事件驱动让淡出恰好发生在用户操作时。**这是针对场景做对了的取舍。** |
| **理由二（为什么是 0.5 不是 0.7）** | **这是全项目唯一有明确调参理由 + commit 记录的参数**。commit `c62d0b6` message：`tune(web/v2-B4): stronger interest decay (0.7 -> 0.5) for profile plasticity`。`profile.ts:216-224` 解释：点击无上限累加，只有衰减能把早期大权重拉回来；0.7 时要太多次刷新，画像感觉被锁死（entrenchment）；0.5 让持续的兴趣转移能在几次刷新内接管。 |
| **动力学（能推出来很加分）** | 设每轮刷新间点击某类 c 次，则 `w ← (w+c)×0.5`，**不动点 w\* = c**。所以稳态权重 ≈ 每轮点击数，天然有界；停止点击后每次减半，约 3–4 次刷新消失。 |
| **代价** | ①只有正反馈，**没有负反馈**（曝光未点击 / 不感兴趣都没建模）；②6 维标量权重，**没有行为序列**；③衰减因子对所有类目一视同仁。 |
| **重做会不会改** | 🟢 **不改**。这是少数几个"有理由、有实验记录、有可推导性质"的决策。<br>**面试时把这一个讲透，胜过把四个拍脑袋的参数都含糊带过。** |

### D3. new/seen 配比 = 80% 🟡

| | |
|---|---|
| **决策** | exploit 的 10 个槽位里，目标 80% 是未看过的（`profile.ts:43` `NEW_RATIO=80`，`mix_op.hpp:70-84`）。 |
| **理由** | `profile.ts:39-42`：留一个 2–3 张的"收藏夹"配额，让刷新不是纯换新，也不是纯重放。 |
| **代价** | 数字是拍的。且 `seenItemIds` **无上限增长**（`profile.ts:205`），每次请求全量序列化成 CSV 跨边界（`App.tsx:72`）。 |
| **重做会不会改** | 🟡 比例靠实验；`seenItemIds` 该加 LRU 上限——🔴 **这个会改**，是疏漏不是取舍。 |

## E. 边界层

### E1. JS↔WASM 用 CSV + JSON 字符串，不做零拷贝 🟡

| | |
|---|---|
| **决策** | 唯一的导出函数收两个 CSV 字符串 + 一个 int，返回一个 JSON 字符串（`bindings.cpp:25-27, 57-59`）。 |
| **理由** | `bindings.cpp:21-24`：6 个 float 这种固定小向量，CSV 是最简单稳健的过界方式——不用 `register_vector`，JS 侧不用手动 `.delete()`。 |
| **代价（实测）** | payload 一次请求物化 **5 遍**：JS string → WASM 堆（embind 拷贝）→ `stof` 逐 token 解析 → `ostringstream` 拼 2,040 字符 → 拷回 JS string → `JSON.parse` 建对象图。**实测边界开销 ≈ 30 µs / 请求，占 JS 侧墙钟 113.74 µs 的 27%**，且 UI 完全没展示。 |
| **重做会不会改** | 🟡 **当前规模不改**。而且**入参方向即使想零拷贝也只能优化那 6 个 float**（`HEAPF32` 视图）；**返回方向做不了**——feed + trace 是变长结构，要么定死二进制布局手工解包，要么就是 JSON。在 2 KB 量级上 JSON 是正确的工程选择。<br>**这是个好答案不是短板**：能说出「我知道这是文本往返，30 µs 在 3,000 候选下不值得优化；真到 BFS 那个量级就得换二进制协议 + arena」，比假装做了零拷贝强。 |

### E2. 引擎无状态，用户画像放前端 🟡

| | |
|---|---|
| **决策** | C++ 每次调用是纯函数 `(weights, seen, ratio) → JSON`，不保存任何用户状态。画像模型、点击累加、衰减、持久化全在 `web/src/profile.ts`。 |
| **理由** | 是 A2（无后端）的必然结果：状态本来就只能在浏览器里。而且引擎无状态天然线程安全、可并发、可复现。 |
| **代价** | **两个排序策略参数住在 TypeScript 里**：`DECAY_FACTOR=0.5`（`profile.ts:225`）和 `NEW_RATIO=80`（`:43`），和引擎的 8 个 `constexpr`（`api.hpp:45-52`）分居两地、两种语言。想调一次策略要看两个文件。 |
| **重做会不会改** | 🟡 **无状态引擎不改**（这是对的）。<br>但**策略参数应该收拢到一处**——这正好和 Step 6(c) 的"图/配置外置"是同一件事：如果有一份声明式配置，这两个参数天然该放进去。 |

### E3. 手写 JSON 序列化 🟢

| | |
|---|---|
| **决策** | `to_json`（`api.hpp:186-221`）用 `ostringstream` 手拼，`json_escape`（`:171-181`）只转义 `"` 和 `\`。 |
| **理由** | `:183-185`：形状小且固定，引入 JSON 依赖不划算。而且引擎不能有重依赖（`CLAUDE.md`）。 |
| **代价** | ①转义**只处理两个字符**——注释说明数据只可能是 ASCII 类目名和固定 label，所以够用，但这是个靠约定维持的不变量；②`ostringstream` 不快，实测 **18.22 µs / 请求**（native），比 FeatureOp+ScoreOp+RerankOp+MixOp 加起来还多；③浮点用默认格式，精度不受控。 |
| **重做会不会改** | 🟢 **不改**。但值得知道 18 µs 这个数——如果哪天要优化整体延迟，`to_json` 比大多数算子更值得动。 |

## G. 这一步最重要的三个结论

1. **「SoA 是为了 SIMD」是错的，必须拆成两句话。**
   实测：AoS 跑**同一个** `dot_simd`，速度几乎一样（9 次试验中位数差 1.7%，
   全距 −4.7%…+4.4%，**跨零**），因为 `float vec[64]` 在 AoS 里同样连续。
   **向量化吃的是 embedding 块连续；SoA 单独买到的是"扫描不加载无关字段"，
   方向清楚（少读 6.2% 字节）但在 768 KB 全进 L2 的规模下测不出来。**

2. **只有一个 🔴：`std::sort` 做 top-k。** 其余决策要么正确，要么是外部
   约束决定的。而这一个的代价被实测量化了——占 recall 80%，换 `nth_element`
   能再快 2.6×，**比 SIMD 带来的收益还大**。

3. **参数层是最脆弱的一层：四个数里三个是拍的**（ScoreOp 权重、λ=0.7、
   探索 2/12），唯一有理由 + commit 记录 + 可推导动力学的是
   `DECAY_FACTOR` 0.7→0.5。**面试策略：主动把 D2 讲透，
   其余三个被问到就直接承认"没有评估手段所以定不了"，
   并说清"要定它需要什么"——这比编依据安全得多，也显得更专业。**
